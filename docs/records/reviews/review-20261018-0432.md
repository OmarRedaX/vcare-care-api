## Refuted / not a defect

- M2 (denied record requests consume no rate budget; timing of resolver queries): not records-specific. Every module mounts `authorize` before the limiter (`consultations`, `patients`, `sessions`, `schedules`, `doctors` routes), spec 3.9 states it deliberately, and `404` bodies are identical for absent and foreign ids, so enumeration reveals nothing by itself (the one real oracle is M1, which is fixed at the resolver). A 1-vs-3-query timing difference over the network is not a practical oracle.
- M4 (timeline embeds profile clinical fields; audit metadata lacks a flag): R-D10 (owner) decided one `patient_records.listed` row per call with no `patient_profile.read`; the profile is included on every successful call, so a `profileIncluded` flag would be constant. The "every access audited" rule is met by the row that exists.
- M6 (`hasRecord` reaches admin viewers): accepted by owner decision 1.5.7; the stated reasoning holds (a boolean, no record content; `record.created` audit rows are readable by admins through `GET /audit-logs`, which has no action restriction). Not re-litigated.
- M8 (pre-lock in-place `PATCH` can commit after a concurrent amendment, and the 200 body shows `amendments: []`): requires two `PATCH`es racing within milliseconds of the exact 24 h lock instant; spec 3.6 step 7 accepts the transaction-start lock semantics (R-D8, owner). The residual claim in step 4 ("a record cannot have amendments before its lock") is true outside that boundary race; no fix is needed beyond optionally loading amendments in the 200 body.
- M10 (100 kb global JSON limit vs maximal record body): the largest schema-valid body is 24,000 code points; raw UTF-8 is at most 96,000 bytes (4 bytes/char), under 102,400, and browsers' `JSON.stringify` emits raw UTF-8. Only ASCII-escaping serializers (`\uXXXX`) of non-ASCII text could exceed it, and the rejection is already the documented `400 ValidationFailed` (`entity.too.large` mapping in `errorHandler.ts`). Not a defect.
- M17 (deferred): `RecordAttachment` still requires `downloadUrl`/`downloadUrlExpiresAt` against ADR 0014, but `MedicalRecord.attachments` is always `[]` (contract line 5324) and no attachment route exists yet; `record-attachments` rewrites the schema. Track in that module, not as a records finding.
- M18 (no cap on amendments per record): spec "Unbounded inputs" (spec.md:489) accepts it with reasoning (doctor-driven, 20 writes/min, page of at most 100 records). Not a defect for MVP; revisit if an amendment-heavy record appears.
- M19 (validating `ADD CONSTRAINT` on `consultations`): the column was unwritable until this unit, so every value is `NULL` and the validation scan is a sequential read of a small pre-release table; `lock_timeout` already bounds the wait. `NOT VALID` followed by `VALIDATE CONSTRAINT` in the same migration transaction keeps the `SHARE ROW EXCLUSIVE` lock until commit (knex migrations are transactional), so it would give no benefit unless split into a separate non-transactional migration. Not worth the churn.
- M20 (`fk_medical_records_consultation_id` covered only by the partial unique index): CLAUDE.md requires an index whose leading column is the FK column, which holds. The only query that would need a full index is the referential check on a `consultations` key delete/update, which never happens (no hard delete, `ON DELETE RESTRICT`, keys immutable), and a second index would violate "indexes exist only for a query in code".

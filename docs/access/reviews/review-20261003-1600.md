## High

- [ ] OPEN — The boot route assertion has four holes, so a route can reach its handler without authorization and the process still boots · `src/lib/rbac/assert-routes-authorized.ts:21-47`
  - Scenario: a throwaway probe with the real function and the real `markGuard`/`markAuthorize` markers booted all four shapes:
    - (a) **Handler before `authorize`.** `router.get("/x", userGuard(), ctrl.method, authorize(p))` passes, because line 36 only requires *some* guard before `authorize`. `ctrl.method` answers any valid token.
    - (b) **Terminal `router.use(path, fn)` inside a module router.** `router.use("/secret", handler)` passes: the layer has no `.route`, and `stackOf(fn)` is `undefined`, so `walk` returns at line 23. The unit test "should ignore router-level middleware that is not a route" codifies this.
    - (c) **Mounted Express 5 sub-app.** `router.use("/x", express())` passes: an Express 5 app exposes `.router` and has no `.stack`, so it is never walked.
    - (d) **`router.route()` chain.** `router.route("/s").get(userGuard(), authorize(p), list).post(create)` passes. Line 29 flattens every method's handlers into one list, so `POST /s` is served with no guard and no policy. The reverse split also passes: `.get(userGuard(), h).post(authorize(p), h2)`. Separate `router.get`/`router.post` registrations are caught.
  - Rule: CLAUDE.md → Authorization — RBAC and ownership (deny by default, fail closed). CLAUDE.md → Module file conventions #7 (guard → authorize → [idempotency] → handler). Spec §3.4.4 / A8.
  - Fix:
    - (a) Every handler before `authorizeAt` must carry the guard marker.
    - (b) Inside module routers (anything below `app.router`'s top level), throw on a non-route, non-router layer unless it is a 4-arity error handler or explicitly marked (`sealRouter` capture, `noStore`).
    - (c) Walk `handle.router` when `handle.stack` is absent.
    - (d) Group `route.stack` by `entry.method` (`undefined` means all methods and applies to each) and check each method separately.
  - Test gap: unit cases for (a)–(d), including both orderings of (d). Replace the "should ignore router-level middleware" test with one that throws for a terminal `use(path, fn)` and passes only for a marked middleware.

## Medium

- [ ] OPEN — `ensure-app-login` can log the app database password when the connection drops mid-DDL · `src/lib/knex/app-login.ts:72-75` → `src/migrate.ts:91-92`, `src/lib/logger/logger.ts:70-75`
  - Scenario: `trx.raw(ddl)` sends `ALTER ROLE "care_app" WITH LOGIN PASSWORD '<secret>'` as literal SQL with no bindings. On any rejection, knex `executeQuery` rewrites the message to `err.message = queryObject.sql + ' - ' + err.message` (`node_modules/knex/lib/execution/internal/query-executioner.js:38-40`); `compileSqlOnError: false` only skips binding interpolation and still prefixes the SQL. If the server answers with a SQLSTATE, `serializeError` drops the message, so that case is safe. A connection loss is different: pg's `Error('Connection terminated unexpectedly')` (`node_modules/pg/lib/client.js:204`) carries no code, and `ECONNRESET`/`ETIMEDOUT` do not match the SQLSTATE pattern. For those, `serializeError` keeps `message`, and `migration_failed { command, error }` writes the full DDL, password included, to stdout and the log store. The redactor matches key names only.
  - Rule: CLAUDE.md → Privacy and logging (never log secrets/tokens). CLAUDE.md → Security rules. ADR 0018 Decision 1 ("the log line carries only `{ created }`"). Spec §7 ("never logged: … the app-login user name or password").
  - Fix: wrap the `trx.raw(ddl)` loop in `try/catch` and rethrow a fixed `new Error("app_login_ddl_failed")` that copies only a SQLSTATE `code` when one is present, never the message.
  - Test gap: a unit test where `raw(ddl)` rejects with a code-less `Error` whose message embeds the DDL. Assert that `ensureAppLogin` rejects with `app_login_ddl_failed`, and that no captured log line contains the password substring.

- [ ] OPEN — The Redis client never drops a stalled or half-open connection, so after an un-RST failover the API stays degraded until the kernel gives up (about 15 min), and the stall test hides this · `src/lib/redis/redis.ts:16-27`, `tests/integration/redis-stall.test.ts:105`
  - Scenario:
    1. The Redis primary disappears without an RST while commands are on the wire, for example a managed failover that retires the node.
    2. `commandTimeout: 500` only rejects the command's promise (`node_modules/ioredis/built/Command.js:191-197`). The socket is not destroyed, `status` stays `ready`, no `close` is emitted, so `retryStrategy` never runs.
    3. `socketTimeout` is not set, although ioredis 5.11.1 supports it (`Redis.js:430-433, 486-497` destroys the stream when no data arrives while commands are queued). `keepAlive: 0` does not help while data is unacknowledged.
    4. Until Linux `tcp_retries2` closes the socket (about 15 min), the breaker half-open probe costs 500 ms every 5 s, idempotency is skipped (`redis_breaker_open`), rate limits fall back to per-process memory, and readiness reports `redis: down`.
    5. In manual QA (observation 1) a byte-dropping proxy also desynchronised the reply queue, and the connection never recovered. Spec §12.3's recovery assertion passes only because the test calls `stalled.disconnect(true)` itself.
  - Rule: CLAUDE.md → API conventions (Redis is Tier 2: degrade, then recover). Spec §12.3 / A19 (recovery after the stall ends). CLAUDE.md → Testing policy (a test must not mask the behaviour it pins).
  - Fix: set `socketTimeout` in `createRedis`, for example `2_000` (above `commandTimeout`, below the readiness budget). Optionally call `client.disconnect(true)` when the breaker opens, so a fresh connection is dialled; `retryStrategy` reconnects it.
  - Test gap: in `redis-stall.test.ts`, remove the manual `disconnect(true)`. Assert that the client reconnects on its own after the proxy forwards again, and that `redis_breaker_closed` is logged within `socketTimeout + REDIS_BREAKER_OPEN_MS` plus a margin.

## Low

- [ ] OPEN — `ensureAppLogin` takes over an existing role without resetting its attributes · `src/lib/knex/app-login.ts:67-70`
  - Scenario: when the role already exists, the code runs only `ALTER ROLE %I WITH LOGIN PASSWORD %L` and `GRANT vcare_app`. A hand-made `care_app` with `CREATEDB`/`CREATEROLE`/`BYPASSRLS` keeps those rights. With a superuser owner (local dev), `DATABASE_URL=postgres://postgres:…` passes the env check, which only requires a user different from the owner. The superuser's password is then reset, it joins `vcare_app`, and `care-api` runs as superuser. That voids the grant-based append-only guarantee of `audit_logs`. On PG16+ a `CREATEROLE`-only owner (production) gets `42501` for roles it does not administer, which limits the risk mostly to dev and test.
  - Rule: CLAUDE.md → Database rules ("Two database roles"). ADR 0018 Decision 1 (`care_app` is `INHERIT NOSUPERUSER NOCREATEDB NOCREATEROLE`). Spec A14.
  - Fix: either make the ALTER path `ALTER ROLE %I WITH LOGIN INHERIT NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS PASSWORD %L`, or refuse (`app_login_role_privileged`) when `pg_roles` shows `rolsuper`/`rolcreaterole`/`rolcreatedb`/`rolreplication`/`rolbypassrls`, or when the role owns objects.
  - Test gap: a `db-roles` integration test that pre-creates the login with `CREATEDB`, runs `ensureAppLogin`, and asserts that `rolcreatedb` is false or that the run is refused.

- [ ] OPEN — The app role can set `id` and `created_at` on `audit_logs`, so it can write back-dated or future-dated audit history · `src/migrations/20261002120100_create_audit_logs.ts:45-47`, `src/migrations/20261002120200_create_audit_logs_ensure_partitions.ts:42`
  - Scenario: the table-level `GRANT INSERT` covers every column. A compromised `care_app` credential, or a future SQL injection, can insert:
    - a `record.read` row dated last year, which cannot be told apart from real history;
    - a row with `created_at = now() + 6 months`, which lands in `audit_logs_default` and makes `audit_logs_ensure_partitions` fail for that month every day;
    - an explicit duplicate `id`, which the `(id, created_at)` PK allows and which breaks the future `(sortValue, id)` cursor.

    `AuditRecorder` never sets these columns (`src/lib/audit/audit.ts:22-23`), so a column-level grant costs the app nothing.
  - Rule: CLAUDE.md → Database rules (`audit_logs` is append-only; the app role has INSERT/SELECT only). ADR 0018 rationale (append-only by grant, not by habit).
  - Fix: add a new migration that revokes the table-level `INSERT` and grants `INSERT (actor_user_id, actor_role, action, entity_type, entity_id, request_id, metadata)` plus `SELECT` on `audit_logs` and `audit_logs_default`. Apply the same column list in the function's per-partition `GRANT` with `CREATE OR REPLACE FUNCTION`, and re-grant the existing monthly partitions.
  - Test gap: in `db-roles`, as `care_app`, `INSERT … (created_at)` and `INSERT … (id)` → `42501`, while `AuditRecorder.record` still inserts.

- [ ] OPEN — Creating a monthly partition with `CREATE TABLE … PARTITION OF` takes `ACCESS EXCLUSIVE` on `audit_logs`, so audit inserts queue behind it for up to 2 s, contrary to the function's comment · `src/migrations/20261002120200_create_audit_logs_ensure_partitions.ts:10, 37-41`
  - Scenario: about once a month, the tick that actually creates a partition waits for `ACCESS EXCLUSIVE` on the parent while any open request transaction holds `ROW EXCLUSIVE` (it has already inserted an audit row). Every new `INSERT INTO audit_logs` then queues behind the waiting lock request until the lock is granted or `lock_timeout 2s` cancels the CREATE. Booking, record, and suspension writes that audit stall for up to about 2 s, which breaks the booking-write budget. An insert issued right as the wait starts can also reach its own 2 s `statement_timeout` and fail with 500. The comment ("lock_timeout 2 s so it never queues behind a long lock and stalls audit inserts") states the opposite.
  - Rule: CLAUDE.md → Performance rules (budgets: booking write < 200 ms p95).
  - Fix: in a new migration (`CREATE OR REPLACE FUNCTION`), create the month as a standalone table (`CREATE TABLE … (LIKE public.audit_logs INCLUDING DEFAULTS INCLUDING CONSTRAINTS)`), then `ALTER TABLE public.audit_logs ATTACH PARTITION … FOR VALUES …`. `ATTACH` takes only `SHARE UPDATE EXCLUSIVE` on the parent, which does not conflict with inserts. Consider a shorter `lock_timeout` (about 200 ms), since the daily tick retries anyway.
  - Test gap: an integration test that holds an open transaction with an audit insert, runs the tick that creates a month, and asserts that a concurrent `AuditRecorder.record` completes in < 200 ms.

- [ ] OPEN — `worker --once audit-partitions` exits 0 when the partitions were not ensured, but the runbook says "exit 0 = ensured" · `src/lib/audit/partition-loop.ts:43-48`, `src/worker.ts:25-31`, `docs/runbook.md:50`
  - Scenario: `ensure()` catches every failure (lock timeout, a `DEFAULT` row in the new month's range, a missing grant), logs `audit_partition_missing`, and returns. The tick resolves, `runOnce` logs `worker_once_completed`, and the process exits 0. An on-call engineer following the `AuditPartitionMissing` runbook sees exit 0 and closes the ticket while the month is still missing. `tasks.md` reports that `--once` exits 1 with Postgres down; that comes from the default-partition `SELECT` throwing, not from `ensure()`. The loop's non-throwing behaviour is correct (spec §3.6 step 2 / A16); the gap is in what `--once` reports.
  - Rule: Spec §3.6 `--once` (exit code reflects the tick); `docs/runbook.md` → `AuditPartitionMissing`.
  - Fix: have `ensure()` return `"ensured" | "locked" | "failed"`. The loop ignores the result; `runOnce` exits 1 on `"failed"`, for example through an optional `WorkerLoop.onceResult`, or by having the partition loop's tick throw only when invoked with a `once` flag. Otherwise, correct the runbook to say "exit 0 and an `audit_partitions_ensured` line".
  - Test gap: `worker-partitions` child-process test where a `DEFAULT` row blocks a new month → `--once audit-partitions` exits 1.

- [ ] OPEN — The JWKS DTO rejects contract-valid documents that carry extra public JWK members, which turns a harmless Identity change into a full 401 outage after the 1 h cap · `src/lib/auth/jwks.dto.ts:32-39`, `src/lib/validation/validate.ts:48-49`, `src/lib/auth/jwks-cache.ts:191`
  - Scenario: the hub copy of Identity's contract (`Jwk`, `../vcare-hub/contracts/identity-service.openapi.yaml:1436-1445`) has no `additionalProperties: false`. If Identity adds `key_ops: ["verify"]` or `x5t`, every refresh fails with `invalid_document`. The cached keys expire after 1 h, and from then on every authenticated request gets 401. This is latent: Identity emits exactly the six members today. Spec line 341 chose `forbidNonWhitelisted`, which contradicts the contract, and the contract wins. `importJWK` receives only the six public fields (`jwks-cache.ts:200`), so stripping unknown members cannot import private material.
  - Rule: CLAUDE.md → Cross-service integration (validate against the contract; a malformed response is a failure, and an extra optional member is not malformed). CLAUDE.md preamble (the contract wins over the spec).
  - Fix: validate the JWKS with `whitelist: true` and without `forbidNonWhitelisted` (a dedicated option on the validation helper, not a copy of it).   - Test gap: a key with `key_ops: ["verify"]` still verifies. A key carrying `d` is still `invalid_document`.

- [ ] OPEN — Tests do not pin the JWKS refresh lifecycle: the interval tick, the body-phase timeout, and the boot wiring can each regress silently · `tests/unit/lib/auth/jwks-cache.test.ts:81-88`, `tests/unit/lib/auth/jwks-fetcher.test.ts:139-144`, `src/server.ts:39, 59`

## Manual-QA observations

1. **ioredis never reconnects after a byte-dropping stall** — **Confirmed, Medium**, recorded above ("The Redis client never drops a stalled or half-open connection"). The proxy's byte-dropping is an artefact, but the same lack of a socket-level timeout leaves a real un-RST failover degraded for about 15 min, and the stall test masks it with `disconnect(true)`.
2. **Malformed `:param` without a token → 400, not 401** — **Dismissed.** Express 5 decodes path params while matching the layer (`node_modules/router/lib/layer.js:72`, `decodeParam` at 219-230 sets `status = 400`), before any route handler runs. Spec §12.1 / A17 define the mapping. Nothing is disclosed: the 400 fires only when the path matches a route pattern, and a well-formed path already shows the route exists (401 vs 404). `errorHandler` returns a fixed detail and never logs the raw value.
3. **`unhandled_error` lacks `route`** — **Confirmed, Low**, recorded above (extended to `error_after_headers_sent` and `rate_limit_internal_error`).

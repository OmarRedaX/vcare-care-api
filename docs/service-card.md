## Responsibilities
The medical marketplace: doctor profiles and credentialing, specialties, working hours, schedule
exceptions and consultation types, computed availability (slots are never stored), booking and the
consultation lifecycle (waiting room, session join, no-show), patient profiles, medical records with a
24 h lock and amendments (built 2026-10-18; doctor read access to a patient's records rides the in-process `consultations` relationship port, and the `records` module adds no external dependency) and PDF/JPEG/PNG file attachments on those records (built 2026-10-20: verified direct upload, audited on-demand download, soft delete before the lock), help articles (the Phase-2 RAG corpus), and the audit log for all of it.

## Data owned
`specialties`, `doctor_profiles`, `doctor_specialties`, `doctor_languages`, `verification_documents` (built), `upload_intents` (built),
`working_hours` (built), `schedule_exceptions` (built), `consultation_types` (built), `consultations` (built), `patient_profiles` (built),
`medical_records` (built), `medical_record_amendments` (built; append-only by grant), `record_attachments` (built 2026-10-20; the app role can read, append six columns and set `deleted_at`; its upload intents live in `upload_intents`, operated by the shared `upload-intents` module), `help_articles`, `audit_logs`,
`identity_sync_jobs` (built; kinds `verification`, `suspension`, `reinstatement`, written by the `identity-sync` engine), `notification_outbox` (built; written by booking, reschedule, cancel, schedule blocks, suspension and the reminder scan; delivered, retried and purged by `care-worker`, which updates only its state columns). Identity accounts are referenced only by `*_user_id BIGINT` (no cross-database FK).
Detail: [architecture/data-model.md](./architecture/data-model.md).

## Depends on
| Dependency | Interface | For | Failure policy |
|---|---|---|---|
| identity-service | `GET /.well-known/jwks.json` (public, port 3000; `IDENTITY_JWKS_URL`) | local verification of user access tokens: in-memory cache refreshed every 5 min (Identity's `max-age`), demand refetch on an unknown `kid` ≤ 1/min | **degrade to cache, fail closed**: cached keys trusted ≤ 1 h after the last successful fetch, then none; no matching key → `401 Unauthorized`, never a skipped verification; readiness reports `checks.identityJwks: up\|down` (informational, never fails readiness); alert `IdentityJwksStale` at 30 min |
| identity-service | `POST /internal/auth/token` (internal, port 3100) | client-credentials service token, scopes `users:read users:status:write` | cached to 30 s before `exp`, single-flight, one refresh on 401; needed by the cases below |
| identity-service | `PATCH /internal/users/:id/status` → `active` / `rejected` / `pending` — **Case 1** | verification decision, re-open, resubmission | **retry-report-pending**: 3 attempts, then 202 `identitySync: pending` + durable job (inserted in the decision transaction; `identity-sync` worker loop retries); Identity 409 (or `400`/`403`/`422`) → `failed` + alert. **Built (2026-10-08)**, engine extracted to the `identity-sync` module (ADR 0021). Provider route not yet deployed in real Identity (404 → keeps retrying) |
| identity-service | `GET /internal/users?ids=` — **Case 2** | display name (`fullName` → `displayName`), avatar on search and lists | **degrade**: cache 300 s, 1 retry, misses render `profileHydrated: false`, never 5xx. **Built** for the admin application queue/detail, the doctor's own application, `GET /api/consultations` + `/{id}`, and the doctor's waiting room and calendar (one batched call per page or response; write responses are not hydrated); provider route not yet deployed in real Identity |
| identity-service | `PATCH /internal/users/:id/status` → `suspended` — **Case 3** | revoke all sessions of a suspended doctor | **must-not-degrade**: ~6 s inline, durable `suspension` job (inserted in the decision transaction) retried without an attempt cap until success (transient failures only; Identity 409/`400`/`403`/`422` → `failed` + page), 503 `IdentityUnavailable` until confirmed, page after 3 failures. **Built (2026-10-09, `admin-doctors`)** |
| identity-service | `PATCH /internal/users/:id/status` → `active` from `suspended` — **Case 4** | reinstate a suspended doctor | **retry-report-pending**: 3 attempts, then 202 + durable `reinstatement` job; ticket alert after 15 min unsynced; doctor unbookable until synced. **Built (2026-10-09, `admin-doctors`)**; real Identity accepts `suspended → active` for doctor targets (Identity ADR 0025) |
| identity-service | `GET /internal/users/contacts?ids=` — **Case 5** (built 2026-10-12; separate service token with only scope `users:contact:read`) | recipient email, name and locale for notifications (`care-worker` only, ≤ 100 ids per call) | **delay**: rows stay `pending` with backoff and the attempt is not consumed; unknown or non-active recipients are `skipped`; never cached, stored or logged. The deployed `care-service` client must hold the scope |
| video room provider | video port (`lib/video`); fake adapter only today (`VIDEO_PROVIDER=fake`, refused in production; env `VIDEO_PROVIDER`, `VIDEO_PROVIDER_KEY`, `VIDEO_JOIN_TOKEN_TTL_SECONDS`) | room creation and per-participant join tokens on `join`/`start` | 2 s bound, never inside a transaction: `503 VideoUnavailable`, consultation state unchanged (before commit) or already valid and repairable by repeating `join` (after); bookings, cancel, complete and no-show unaffected |
| email provider | email port (`lib/email`), via `notification_outbox` + `care-worker`; log-only adapter today, no real provider yet | booking confirmation, 24 h and 1 h reminders, reschedule, cancellation, schedule block, `doctor_suspended` notice, "doctor joined" (producer built with sessions, queued on `start`) | outbox retries, `dead` after 8; never blocks or rolls back a booking |
| object storage | storage port (`lib/storage`, AWS SDK v3); browsers use presigned URLs directly (hub ADR 0011) | verification documents, record attachments | `complete` or `download-url` fails; a failure before the promote can be retried with the same upload, one inside the short post-promote transaction needs a fresh upload (runbook, spec 14.2 K1); no row is created without a verified object. **Built** for verification documents and, since 2026-10-20, record attachments (`record-attachments`; both through the shared `upload-intents` flow, ADR 0022; local dev/test: MinIO). Reading a record makes no storage call |

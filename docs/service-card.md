## Responsibilities
The medical marketplace: doctor profiles and credentialing, specialties, working hours, schedule
exceptions and consultation types, computed availability (slots are never stored), booking and the
consultation lifecycle (waiting room, session join, no-show), patient profiles, medical records with a
24 h lock and amendments (built 2026-10-18; doctor read access to a patient's records rides the in-process `consultations` relationship port, and the `records` module adds no external dependency) and PDF/JPEG/PNG file attachments on those records (built 2026-10-20: verified direct upload, audited on-demand download, soft delete before the lock), admin-authored help articles for patients and doctors, which are also the Phase-2 RAG corpus (built 2026-10-29: Markdown stored verbatim, edited in place, soft delete, admin-managed; `GET /internal/help-articles` for the assistant is designed, not built), and the audit log for all of it.

## Data owned
`specialties`, `doctor_profiles`, `doctor_specialties`, `doctor_languages`, `verification_documents` (built), `upload_intents` (built),
`working_hours` (built), `schedule_exceptions` (built), `consultation_types` (built), `consultations` (built), `patient_profiles` (built),
`medical_records` (built), `medical_record_amendments` (built; append-only by grant), `record_attachments` (built 2026-10-20; the app role can read, append six columns and set `deleted_at`; its upload intents live in `upload_intents`, operated by the shared `upload-intents` module), `help_articles` (built 2026-10-29; soft delete, the app role has no `DELETE`), `audit_logs`,
`identity_sync_jobs` (built; kinds `verification`, `suspension`, `reinstatement`, written by the `identity-sync` engine), `notification_outbox` (built; written by booking, reschedule, cancel, schedule blocks, suspension and the reminder scan; delivered, retried and purged by `care-worker`, which updates only its state columns). Identity accounts are referenced only by `*_user_id BIGINT` (no cross-database FK).
Slots are never stored; the only derived data is in Redis (`slots:*`, `slots-ver:*`, `next-available:index`, `free-map:*`, `next-available:refresh`, `next-available:swept-at`, `name-index`, `name-index:building`, `name-index:built-at`, all rebuildable and written by `care-api` and `care-worker`; env `SLOT_CACHE_TTL_SECONDS` (1 to 60, default 60), `AVAILABILITY_SWEEP_INTERVAL_SECONDS` (120), `AVAILABILITY_NAME_REFRESH_SECONDS` (300; refresh + sweep interval + 60 must stay below the 900 s index TTL, checked at boot), `AVAILABILITY_INLINE_MISS_CAP` (20)).
Detail: [architecture/data-model.md](./architecture/data-model.md).

## Depends on
| Dependency | Interface | For | Failure policy |
|---|---|---|---|
| identity-service | `GET /.well-known/jwks.json` (public, port 3000; `IDENTITY_JWKS_URL`) | local verification of user access tokens: in-memory cache refreshed every 5 min (Identity's `max-age`), demand refetch on an unknown `kid` ≤ 1/min | **degrade to cache, fail closed**: cached keys trusted ≤ 1 h after the last successful fetch, then none; no matching key → `401 Unauthorized`, never a skipped verification; readiness reports `checks.identityJwks: up\|down` (informational, never fails readiness); alert `IdentityJwksStale` at 30 min |
| identity-service | `POST /internal/auth/token` (internal, port 3100) | client-credentials service token, scopes `users:read users:status:write` | cached to 30 s before `exp`, single-flight, one refresh on 401; needed by the cases below |
| identity-service | `PATCH /internal/users/:id/status` → `active` / `rejected` / `pending` — **Case 1** | verification decision, re-open, resubmission | **retry-report-pending**: 3 attempts, then 202 `identitySync: pending` + durable job (inserted in the decision transaction; `identity-sync` worker loop retries); Identity 409 (or `400`/`403`/`422`) → `failed` + alert. **Built (2026-10-08)**, engine extracted to the `identity-sync` module (ADR 0021).

## Owner decisions (not OPEN findings: the fix would change a documented decision, the behaviour-preserving extraction, or the golden statement test)
- **K1 (Medium if taken as a defect).** `UploadIntentsService.complete` deletes the quarantine object right after `promote`, before the short transaction (`upload-intents.service.ts:59`). If the transaction then fails for a reason other than the cap race (deadlock, connection reset, audit insert error), the intent stays open but its only copy of the bytes is gone; the retry answers `400 ValidationFailed` and the doctor must re-upload. Inherited unchanged from `main` (`verification.service.ts:116-117`); spec SD3 and the section 4.6 failure table document "intent stays open, quarantine object gone, retry answers `400`" for the short-transaction failures. Moving the delete after commit would change verification's behaviour, which section 2 forbids in the extraction ("storage order unchanged"); it needs a deliberate follow-up that moves the delete after commit (best-effort, `upload_orphan_cleanup_failed`) and adds the test "short tx throws, retry of the same `uploadId` returns `201`".
- **K2 (Low).** The delete-after-lock verdict (`findLockRowForNoKeyUpdate`) and the trigger use the transaction-start `NOW()`, so a `DELETE` that blocks on a concurrent `PATCH`/`complete` of the same author across `locked_at` is accepted up to the lock-wait (bounded by the 2 s statement timeout) after the lock. Spec 3.1 deliberately fixes "same clock as the service (the transaction's `NOW()`)", the same convention as the records trigger; a fix (`clock_timestamp()` in the verdict and the trigger) needs a new migration and changes that convention.
- **K5 (Low).** The purge loop holds the singleton lock connection while doing serial `storage.delete` (2 s timeout) for up to 500 intents, and under a storage outage retries the same oldest 500 rows each tick. The loop was moved unchanged (spec section 2) and the golden `purge` entry pins its statement sequence (singleton lock `1103`, then per-intent lock `1101`); any restructuring (release between intents, cursor) changes that sequence. Reaching the starvation case needs more than 500 expired open intents plus a storage outage.
- **K6 (Low).** `listExpiredOpenIntents` selects every `INTENT_COLUMNS` entry including the clinical `description`, although the purge uses only `id` and `quarantine_key`. The golden `purge` entry pins the full column list; selecting two columns changes the golden JSON. The text is held in worker memory only and is not logged (`upload_intent_purge_failed` logs the error, not the row).

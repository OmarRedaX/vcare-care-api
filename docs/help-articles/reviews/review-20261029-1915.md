## Medium
- [ ] OPEN — A timestamp cursor with year `0000` passes validation but Postgres rejects it, so the request ends as `500 InternalError` instead of `400 ValidationFailed` · `src/lib/http/pagination/cursor.ts:47-56` (reached via `decodeKindedTimestampCursor` :69-78), bound at `src/app/help-articles/repository/help-articles.repo.ts:67`
  - Scenario: an authenticated caller sends `?cursor=` base64url of `["published:0000-01-01T00:00:00.000000Z", 1]` (admin: `updated:`). `TIMESTAMP_CURSOR_PATTERN` matches (`\d{4}`), `new Date("0000-01-01T00:00:00.000Z").toISOString()` round-trips (verified in node), so the cursor is accepted. The repo binds it as `?::timestamptz`; against `care_test`, `SELECT '0000-01-01T00:00:00.000000Z'::timestamptz` fails with `date/time field value out of range`. `errorHandler` has no pg-error mapping, so the response is `500 InternalError` and an `unhandled_error` log line at `error` level (alert noise, user-triggerable). The same shared function backs `decodeTimestampCursor`, so `GET /api/consultations` (`consultations.repo.ts:151`) and the patient record list (`medical-records.repo.ts:114`) have the identical defect. Year 0001 and 9999 are accepted by Postgres and are not affected.
  - Rule: CLAUDE.md → API conventions (pagination: an invalid cursor is `400 ValidationFailed`, `cursor: is invalid`); spec §3.7 (a timestamp cursor must be a real instant).
  - Fix: in `assertTimestampCursorValue`, also reject a year below 0001 (e.g. `parsed.getUTCFullYear() < 1`, or tighten the pattern to `(?!0000)\d{4}`), once, in the shared function so all three modules are fixed.
  - Test gap: `tests/unit/lib/http/pagination.test.ts` has no year-`0000` case for `decodeTimestampCursor` / `decodeKindedTimestampCursor`; add one, plus an integration case per list (help-articles, consultations, records) expecting `400` with `cursor: is invalid`.

## Docs
- [ ] OPEN — `docs/availability/manual-qa.md:418` states "Responses carry `Cache-Control: no-store` (the application default)", which is no longer true for the doctor discovery routes · `docs/availability/manual-qa.md:418`
  - Scenario: before 50f6e6e a pathless `router.use(noStore())` in the verification router stamped `no-store` on every request that fell through to later-mounted routers, which included `GET /api/doctors`, `/api/doctors/:id`, `/api/doctors/:id/slots` (availability is mounted after verification in `src/routes.ts`). After the fix they carry no `Cache-Control` header. A reader of the QA record, or the next QA run, would expect `no-store` and report a false defect. The contract never declared a header for these routes, and `docs/availability/spec.md:486` lists `no-store` for non-clinical routes as out of scope, so only the QA line is wrong.
  - Rule: CLAUDE.md → Documentation structure (docs mirror the as-built behaviour).
  - Fix: reword the line to say discovery routes set no `Cache-Control` of their own (not in `NO_STORE_PREFIXES`), and set `last_verified`.
  - Test gap: none.
- [ ] OPEN — The contract's shared error responses and `NoContent` declare `Cache-Control: no-store`, but every response under `/api/help-articles` (errors and the `DELETE` 204 included) is `private, no-cache`, and the contract does not say so · `contracts/openapi.yaml` (tag `help-articles` ~67; `listHelpArticles` ~2803; shared responses `NoContent` ~3425, `ValidationFailed`, `Unauthorized`, `Forbidden`, `NotFound`, `Conflict`, `RateLimited`), `src/app.ts:42-44`, `src/lib/http/private-no-cache.ts:10`
  - Scenario: a client or conformance tool reads the contract and expects `no-store` on a help-articles `404` or on the `DELETE` `204`; the server sends `private, no-cache`. The difference is called "accepted and documented" in `docs/help-articles/spec.md` (C5 note), but the contract is the source of truth and carries no such note; `tests/unit/contract/help-articles-contract.test.ts` asserts the header on success responses only.
  - Rule: CLAUDE.md → API conventions / Documentation structure (the contract wins; spec mirrors the contract).
  - Fix: add one sentence to the `help-articles` tag description (or the operation descriptions): "Every response under `/api/help-articles`, errors and `204` included, carries `Cache-Control: private, no-cache`, regardless of the shared response headers."
  - Test gap: optionally assert in `help-articles-contract.test.ts` that the tag description mentions the error-response header.

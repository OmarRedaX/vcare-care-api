## High
- [x] RESOLVED — `NotBlank` decorator (src/lib/validation/string-decorators.ts) on `SuspendDoctorDto`, `ReinstateDoctorDto`, `ApplicationRejectDto` and the non-empty `ApplicationApproveDto.note`; the engine falls back to the job kind when the stored reason is blank or blank after the clamp (identity-sync.service.ts:82-83); the fake Identity mirrors `\S`; DTO, engine and integration tests added. Original: A whitespace-only `reason` passes Care's DTO but Identity rejects it with `400`, so a must-not-degrade suspension (and reinstatement) can never be confirmed and is retried forever · `src/app/admin-doctors/dto/admin-doctors.request.dto.ts:7-8` (also `src/app/identity-sync/service/identity-sync.service.ts:80`)
  - Scenario: admin sends `PATCH /api/admin/doctors/9/suspend {"reason":"   "}` (3 spaces, or U+3000, which is not a control character). `CodePointLength(3,2000)` and `NoControlCharacters("all")` pass; the profile is suspended locally and a job is enqueued. The engine sends `reason:"   "`; Identity's `InternalStatusChangeDto` has `@Matches(/\S/, "must not be blank")` and answers `400 ValidationFailed`. `setUserStatus` returns `transient` (see the next finding), so the job reschedules forever with the same body. The admin gets `503`; a repeat suspend is the S6 no-op `503`; Identity sessions are never revoked and the admin cannot fix the reason (the job keeps its stored text). Same for reinstate (`202 pending` forever) and for verification reject (`ApplicationRejectDto`, same validators). The clamp can also yield a blank string: 500+ leading spaces followed by text clamps to spaces only.
  - Rule: Cross-service integration (Case 3 must-not-degrade; the call must be able to succeed); spec S4/BR19 (Identity-bound reason must be acceptable to Identity).
  - Fix: add `@Matches(/\S/)` to `SuspendDoctorDto`, `ReinstateDoctorDto` and `ApplicationRejectDto`; in the engine fall back to `job.kind` when the clamped reason has no non-whitespace character.
  - Test gap: DTO test for `"   "` and `"　　　"` on both routes (400); engine test with a stored blank reason sends the fallback text; fake Identity should mirror the `\S` rule (it only mirrors the length rule today).

## Medium
- [x] RESOLVED — owner decision YES: new `permanent` outcome for HTTP 400/403/422 (identity-client.ts), engine marks job and profile `failed` with `last_error_code=HTTP_<n>` and logs `IdentitySyncTransitionRejected` with kind and code, for all kinds; 404/429/5xx/network/401-after-refresh/malformed stay transient; spec D1/BR5, runbook, ADR 0021 and contract text updated; client, engine and integration tests added. Original: `IdentityClient.setUserStatus` returns `outcome:"transient"` for permanent Identity answers (`400`, `401` after the one refresh, `403`, `422`), so the engine retries them forever · `src/lib/identity-client/identity-client.ts:49-51`, `src/app/identity-sync/service/identity-sync.service.ts:97-106`
  - Scenario: the inner loop breaks on a non-retryable code but falls through to `return { outcome: "transient" }`. Only `409 InvalidStatusTransition` ever reaches `failed`. Any contract drift or validation mismatch (previous finding, a `403 Forbidden` for a non-doctor target under ADR 0025, a `400` after an Identity DTO change) loops every poll with no `IdentitySyncTransitionRejected` page. Suspension at least pages via `IdentitySuspensionSyncFailing` (3rd failure, then every 10th) with `last_error_code=HTTP_400`; reinstatement only raises the 15-minute ticket and approval likewise. The client code is unchanged from main, but admin-doctors makes it reachable on the must-not-degrade path.
  - Rule: CLAUDE.md Cross-service integration (callers treat Identity's non-retryable codes as non-retryable); spec BR5 covers `409` only, so this needs an owner call.
  - Fix: add a `permanent` outcome (HTTP `400/403/422`, not `404/429/5xx/network`) that the engine maps to job and profile `failed` plus a page, exactly like `rejected-transition` with `last_error_code=HTTP_<n>`. Keep `404` transient (the runbook documents "Identity internal-users not deployed yet"). This changes spec D1 ("unbounded retry"), so record it in the spec.
  - Test gap: client unit test for `400/403/422` returning the new outcome (no retry); engine integration test that a `403` ends in `failed` with the page log and no further PATCH on the next tick.

## Low
- [x] RESOLVED — the lock callback now returns true when the job was already settled or superseded, so `syncNow` answers from the re-read profile (identity-sync.service.ts:72-75); engine test per kind. Original: `syncNow` reports `pending` (suspend `503`, reinstate `202`) when the lock-callback returned early because the worker had already settled the job · `src/app/identity-sync/service/identity-sync.service.ts:56,74-77,110`
  - Scenario: decision commits with `next_attempt_at = now`; the worker tick (every 10 s) takes the job first and succeeds. The inline `attempt` then sees `job.status !== pending`, returns `undefined` (so `locked:false`), and `syncNow` answers `202 pending` / `503` although the profile is already `synced`. A blind retry returns the `200` no-op, so it self-heals, but the admin is told revocation is unconfirmed (and a page-grade `503` is logged) for a confirmed suspension. Narrow window; the same path covers "superseded".
  - Rule: spec §3.2/§3.3 (report what Identity confirmed); BR8.
  - Fix: distinguish "lock contended" from "job already settled" in the `attempt` result and, for settled, derive the response from the re-read profile (`synced` leads to 200/confirmed).
  - Test gap: engine test where the job is `succeeded` before `syncNow` runs: expect `200`/confirmed.

# foundation — Code Review

_Against: docs/foundation/spec.md + contracts/openapi.yaml + CLAUDE.md • Dimensions: correctness, security-rbac-clinical, domain-rules, perf-indexing, contract-drift • Verified: adversarial (scratch reproductions against knex 3.3.0 / pg 8.23.0 / express 5.2.1 / router 2.2.0 / Node 24.11 and the local test Postgres + Redis)_

**Latent** means the defect is in shared `lib/` code but no route that reaches it is mounted on today's foundation
surface (health only). It becomes reachable as soon as the first module mounts routes, so it must be fixed before then.
**Spec/contract first** means the fix changes behaviour that `spec.md` or `contracts/openapi.yaml` currently
describes. Change that document before the code (CLAUDE.md → Build order for a new module, step 0).

## Critical
- [ ] OPEN — [Critical, latent] Postgres data-exception messages carry request values into the logs (known bug #1) · `src/lib/logger/logger.ts:25-36`, `src/lib/error/errorHandler.ts:49` (also `:32`, `:41`), `src/server.ts:78,82`, `src/worker.ts:46,50`, `src/lib/worker/loop-runner.ts:77`, `src/migrate.ts:80`
  - Scenario: a request value reaches a query that fails with a class-22 data exception. Postgres puts the value into its own error message: `22P02 invalid input syntax for type integer: "<value>"`, `22007 … timestamp with time zone: "<value>"`, `22008 date/time field value out of range: "<value>"`, `22003 value "<value>" is out of range`. For example, a future `dateOfBirth: "1990-02-30"` passes an ISO-date regex DTO and then fails in PG with 22008. Knex prefixes the SQL text to `err.message` (`knex/lib/execution/internal/query-executioner.js:36-45`). `serializeError` keeps both `message` and `stack`, and the V8 stack header is formatted lazily, so it repeats the rewritten message (reproduced). `errorHandler` then logs the value as `unhandled_error`. The same path applies to `uncaught_error`, `worker_tick_failed` and `migration_failed`. The result is PII or clinical text in logs. Today only the test router `/api/__test/db-cast` reaches it, and the bug is pinned by `test.failing` at `tests/integration/logs.test.ts:114`.
  - Verification note: the wider candidate claim is **refuted** for care's knex 3.3.0. It said that any failed query (statement timeout, CHECK, FK, UNIQUE) logs all bound values. That does not happen: `enrichQueryObject` runs `client.positionBindings()` (pg dialect, `?`→`$n`) before `executeQuery`, so `formatQuery` finds no `?` and interpolates nothing. The scratch run logged `select $1::int - …` and `insert … values ($1, $2, $3) - new row … violates check constraint "…"` with no value. The identity reviewer is right: bindings are not interpolated. For CHECK, NOT NULL and UNIQUE violations the values sit in pg's enumerable `detail` ("Failing row contains (…)"), which `serializeError` already drops. That is still a risk under other log keys (see Low: redaction of Error objects). One edge case remains: an escaped `\\?` (jsonb `?` operator) survives `positionBindings` as a literal `?`, and `formatQuery` would then interpolate binding 0 there.
  - Rule: CLAUDE.md → Privacy and logging ("Never log clinical data or PII"); spec §3.4.3 ("never … `err.message` of non-`AppError` errors"), §3.3 migrate ("no SQL values").
  - Fix: **spec first.** Spec §3.4.4 defines `serializeError` as `{ name, message, code?, stack? }`, which is the leak. Change it so that errors that are not `AppError` and carry a pg SQLSTATE (`/^[0-9A-Z]{5}$/`) or come from knex serialize as `{ name, code, severity?, constraint?, table?, column?, routine? }`, with **no `message`** and a stack rebuilt as `name` + frame lines only (drop line 1). Consider applying that stack rule to every non-`AppError` error in production. Optionally set `compileSqlOnError: false` in `createKnex` to close the `\\?` edge case. Apply the same change in identity (parity; identity has the same Knex SQL-in-message path).
  - Test gap: unit `serializeError` on a pg-shaped error whose `message` was mutated after construction, asserting the value is absent from `message` and `stack`. Integration cases for 22P02, 22007 and 22008 with a fixture value, plus a CHECK violation, asserting the fixture is not in the captured logs. Flip `logs.test.ts:114` from `test.failing` to `it`.

## High
- [ ] OPEN — [High, latent] Idempotency never settles when the client disconnects before the response, so retries get `409` for 60 s and then re-run the handler · `src/lib/idempotency/idempotency.ts:148-168` (also `:109-117`)
  - Scenario: a patient's app sends `PATCH /consultations/:id/cancel` with `Idempotency-Key: K`, times out at 10 s and aborts, and the handler commits at 12 s. Node emits only `close`, never `finish`, for an aborted response (reproduced: events `['close@notEnded', 'handler-json']`). No `done` record is stored and the `in_progress` lock is not released. Every retry for 60 s gets `409 Conflict` with `Retry-After: 1`. After the lock expires the handler runs again: cancel now answers `409 InvalidTransition` instead of replaying the original 200, and reschedule re-executes (duplicate audit row and notification unless the service no-ops). Timeout-then-retry is the main case idempotency exists for. A second trigger leaves the same orphan lock: `SET NX` times out client-side at 500 ms (`commandTimeout`) but lands in Redis, so the middleware logs `idempotency_skipped`, runs the handler with no settle hook, and the orphan `in_progress` blocks retries for 60 s.
  - Rule: CLAUDE.md → Domain rules 5 ("transactional and idempotent on `Idempotency-Key`"), API conventions → Idempotency ("same key + same body → replay original response"); spec §3.4.10 rows 6–6b, F12.
  - Fix: **spec first.** Spec §3.4.10 rows 6a/6b say "on `finish`". Change them to settle once when the handler completes the response, not when the socket finishes. Wrap `res.end` (and keep the `res.json` capture) and store or release from there, using `res.statusCode` and the captured body with a settle-once flag. Keep `finish` only as a fallback. If `acquireLock` throws, issue a best-effort `DEL` of the key before `skip()`, or still register the settle hook.
  - Test gap: integration test with a slow handler and a supertest request aborted via `.timeout()`. A retry after the handler finished must replay the stored 2xx, and the handler call count must stay 1. Unit test with a `SET` that rejects but whose effect lands: the retry must not get 60 s of `409`.

## Medium
- [ ] OPEN — [Medium] Graceful shutdown hangs on keep-alive sockets that carried an in-flight request, so it exits 1 after the full timeout · `src/lib/lifecycle/graceful-shutdown.ts:15-42`, `src/server.ts:16,21`
  - Scenario: SIGTERM arrives (scale-in, deploy, or `shutdown("uncaught_error")`) while a request is in flight on a keep-alive connection (`keepAliveTimeout` 65 s). `server.close()` and the single `closeIdleConnections()` skip that socket because it is active. After the response the socket goes back to idle but stays open, so the `close` callback never fires. Shutdown waits the whole `SHUTDOWN_TIMEOUT_MS` (10 s), logs `error shutdown_timeout {unfinishedRequests: 0}`, calls `closeAllConnections()` (cutting any request that arrived on a surviving keep-alive socket in the meantime), and exits 1. Reproduced on Node 24.11: the response arrived at 325 ms and the drain still hit the timeout. The impact depends on how much traffic is still on the task at SIGTERM (ALB deregistration delay, internal listener), but the timeout alert fires on every such shutdown.
  - Rule: spec §3.4.13 / F19; CLAUDE.md → API conventions (health split, ADR 0006 readiness drains traffic).
  - Fix: **spec first** (§3.4.13 step 2 describes the current single call). During shutdown, set `Connection: close` on responses (in `inFlight()` when `state.isShuttingDown()`), and call `closeIdleConnections()` again whenever the in-flight count reaches 0 (after `whenIdle()`). Bound the timeout on in-flight requests, not on the `close` callbacks. Identity has the same bug; fix both.
  - Test gap: `graceful-shutdown.test.ts` covers only idle servers. Add a real `http.Server` test with a keep-alive agent and a slow request, SIGTERM mid-request, and assert shutdown completes well under `timeoutMs`, logs no `shutdown_timeout`, and exits 0. `process.test.ts:95` sends SIGTERM only when idle.

- [ ] OPEN — [Medium] No client-side connect or query timeout and no TCP keepalive on pg; resource close during shutdown is unbounded · `src/lib/knex/knex.ts:24-48`, `src/lib/lifecycle/graceful-shutdown.ts:44-50`
  - Scenario: an RDS failover or network partition with no RST. pg defaults (`connectionTimeoutMillis` 0, `query_timeout` false, `keepAlive` false; `node_modules/pg/lib/client.js:95-116`) mean in-flight queries on the old primary hang until the kernel's TCP retransmission gives up (about 15 min on Linux). `statement_timeout` is server-side and cannot fire. Those connections occupy the pool, new acquires fail after 1 s with 500s, and readiness stays 503 long after the new primary is up. That can use a third of the 43-min monthly budget (ADR 0005). On shutdown, `db.destroy()` waits for the hung connections (tarn `destroy` waits on `used`), so the process overruns `SHUTDOWN_TIMEOUT_MS` and is SIGKILLed. Secondary issue (was P5): with a cold pool (`min: 0`), each new connection runs 2 serial `SET`s in `afterCreate` inside the 1 s acquire window, which widens the post-idle `KnexTimeoutError` window seen in identity.
  - Rule: CLAUDE.md → Performance rules 4; ADR 0005/0006 availability; spec §3.4.8 / §3.4.13.
  - Fix: **spec first** (§3.4.8). Set `connection.connectionTimeoutMillis: 2000`, `keepAlive: true`, `keepAliveInitialDelayMillis: 10000`, `query_timeout: statementTimeoutMs + 1000` (when not null), and `pool.createTimeoutMillis: 2000`. Move `TimeZone`/`statement_timeout` into `connection.options: "-c TimeZone=UTC -c statement_timeout=…"` to drop the two round-trips. Bound `closeResources` by the remaining shutdown deadline.
  - Test gap: unit assertions on the `createKnex` config, plus an integration test against a TCP server that accepts and never replies, asserting the query fails within about `statementTimeoutMs + 1 s`.

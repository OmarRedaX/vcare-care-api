ORIGINAL FINDING: · Sweep removes index members using the bookable list it snapshotted at the start of the pass, so a doctor who became bookable (and was freshly written by refresh or inline compute) during the pass is `ZREM`ed and its free-map deleted · `src/app/availability/service/availability-sweep.service.ts:35,47-49` -> `src/app/availability/service/next-available.index.ts:144-151`
  - Scenario: sweep snapshots at t0; at t1 an approval/reinstatement sync completes, `DoctorChangeListener` queues the doctor; refresh writes the entry at t2; at the end of the pass (tens of seconds at thousands of doctors) `members()` returns that doctor, which is not in the t0 set, so `remove(stale)` deletes it. Until the next refresh trigger or sweep (up to `AVAILABILITY_SWEEP_INTERVAL_SECONDS` plus the pass time) the doctor is an index miss: it ranks via inline compute only within the 20-per-request cap, and under a window filter it is excluded beyond the cap (flagged `availabilityFilter`).   - Rule: spec AV-R23 ("removes index members that are no longer bookable"); CLAUDE.md -> Domain rules 6.
  - Fix: before removing, re-check the stale ids: `const still = await this.reader.listBookableForIndex(stale)` and remove only `stale` minus `still.items` (one extra query, only when `stale` is non-empty).
  - Test gap: sweep unit test where a doctor appears in `members()` and in the re-check list (became bookable mid-pass) and must not be passed to `remove`.

## Low
- [ ] OPEN — `replaceNameIndex` swap `MULTI` does not abort when `RENAME` fails: the old live index gets its TTL extended and `built-at` is stamped although the method returns false · `src/app/availability/service/next-available.index.ts:237-239`
  - Scenario: `name-index:building` disappears between `EXPIRE building 600` (line 236) and the `MULTI` (eviction under `maxmemory`, failover, or a second worker's `DEL name-index:building` after a lost advisory lock). Redis runs every queued command of a `MULTI` even when one fails: `RENAME` errors, `EXPIRE name-index 900` still renews the previous good index, `SET name-index:built-at` is stamped fresh. The method returns false (the per-entry error check at line 240 works), the sweep logs `availability_name_index_failed`, but AV-R28's "previous build kept, no TTL extension" no longer holds and the retry waits a full `AVAILABILITY_NAME_REFRESH_SECONDS` (300 s) because `built-at` now looks fresh.
  - Rule: spec AV-R28 (failed rebuild keeps the previous build, no TTL extension; retry when due).
  - Decision: plain code fix (the spec's `MULTI` shape in 12.3 should then be reworded to match).
  - Fix: `RENAME` preserves the source key's TTL, so set `EXPIRE name-index:building 900` (not 600) immediately before the swap and make the swap a plain `RENAME`; stamp `name-index:built-at` (`SET ... EX 900`) only after `RENAME` resolved. A failed `RENAME` then touches nothing.
  - Test gap: unit test of `replaceNameIndex` where the `exec()` result has a `RENAME` error entry: assert the method returns false and that `name-index` TTL and `built-at` are unchanged (integration: `DEL name-index:building` between the last chunk and the swap).

- [ ] OPEN — `name-index:building` holds display names with no TTL until after the last `ZADD` chunk; a failed chunk or a worker stop mid-loop leaves them in Redis indefinitely · `src/app/availability/service/next-available.index.ts:230-236`
  - Scenario: `DEL building`, then chunks of 500 `ZADD`; `EXPIRE building 600` runs only after the loop. A Redis timeout/reset on chunk N (`tryRedis` returns `{ok:false}`) or a SIGTERM during the loop leaves a partial `building` key with names and no TTL. The next rebuild `DEL`s it, but if the worker does not run again (decommissioned, Redis recovered but worker stopped) the names stay. AV-R29 promises names exist in Redis for at most 15 minutes.
  - Rule: spec AV-R29; CLAUDE.md -> Privacy and logging (derived Identity data is TTL-bound).
  - Decision: plain code fix.
  - Fix: apply the TTL with the first chunk (`MULTI` of the first `ZADD` + `EXPIRE building 600`, or `EXPIRE` after every chunk), and on any failure inside the loop `DEL name-index:building` best effort. Combine with the previous item's `EXPIRE 900` before the swap.
  - Test gap: unit test where the second `ZADD` rejects: assert the building key has a TTL (or was deleted).

- [ ] OPEN — `AVAILABILITY_NAME_REFRESH_SECONDS` (1..86400) is not constrained against the fixed 900 s index and `built-at` TTL (and against `AVAILABILITY_SWEEP_INTERVAL_SECONDS`) · `src/lib/config/env.ts:135-136`, `src/app/availability/constants.ts:38`
  - Scenario: `AVAILABILITY_NAME_REFRESH_SECONDS=850` with the default 120 s sweep: the next rebuild is due at the 960 s tick, the index expired at 900 s, so every cycle has about 60 s where the name filter is headline-only (`meta.degraded: ["nameFilter"]`) although Identity and Redis are healthy. The same happens with defaults when `AVAILABILITY_SWEEP_INTERVAL_SECONDS` is raised above about 600 s (rebuild period = sweep interval, TTL 900 s with the 300 s refresh gating nothing).
  - Rule: CLAUDE.md -> Env (every variable declared and validated in `lib/config/env.ts`); spec AV-R28.
  - Decision: plain code fix (owner may instead prefer deriving the TTL from the refresh period; either removes the footgun).
  - Fix: a zod `superRefine` on the env object requiring `AVAILABILITY_NAME_REFRESH_SECONDS + AVAILABILITY_SWEEP_INTERVAL_SECONDS + margin (60) < NAME_INDEX_TTL_SECONDS`, or derive `NAME_INDEX_TTL_SECONDS = 2 * refresh + sweep interval` and pass it in.
  - Test gap: env test rejecting a refresh/sweep pair whose sum reaches the TTL.

- [ ] OPEN — `readNameMatches` truncates silently at `NAME_MATCH_LIMIT = 5000` (alphabetical), with no flag and no log · `src/app/availability/service/next-available.index.ts:207`, `src/app/availability/constants.ts:35`
  - Scenario: with more than 5,000 bookable doctors whose normalised names share a 2-character prefix (for example every name starting with a common title prefix) the query `ZRANGEBYLEX ... LIMIT 0 5000` returns the first 5,000 members in name order. Doctors beyond that are missing from the name match and are not matched by headline either: the search returns a wrong (incomplete) set with `meta.degraded` absent. Unreachable at the planned 2.5 k doctors; reachable between the 6 k revisit trigger and the 10 k candidate cap. Each such request also parses up to 5,000 members in Node (a few ms of event-loop time), which is acceptable.
  - Rule: spec AV-R27 (a doctor whose name starts with the prefix matches); CLAUDE.md -> Domain rules 21 (filterable lists).
  - Decision: owner decision (the 5,000 limit is written into spec 12.3). Cheapest options: fetch `limit + 1`, and on overflow log `availability_name_match_truncated` plus add `nameFilter` to `meta.degraded`; or only document the limit next to the 6 k revisit trigger in `docs/architecture/capacity.md`.
  - Fix: as above (a one-line `LIMIT 0 5001` and a branch in `readNameMatches`/`DiscoveryService`).
  - Test gap: unit test with 5,001 members under one prefix asserting the overflow is signalled.

## Docs
- [ ] OPEN — The "renamed doctor matches the old name for up to 5 minutes" guarantee is too optimistic; real worst case is about 11 minutes · `contracts/openapi.yaml:3302-3313` (`NameFilter`), `docs/availability/spec.md` (C6 note, AV-R28/AV-R29), `docs/adr/0025-derived-name-index.md` (Consequences)
  - Scenario: the builder reads names through `identity:user:<id>` (TTL 300 s, `identity-client.ts` `setex(..., 300, ...)`), and rebuilds only on sweep ticks (120 s) once `built-at` is >= 300 s old, so rebuilds happen about every 360 s. A doctor renamed at Identity just after the cache entry was filled is copied under the old name by a rebuild at t = 299 s and is corrected only by the rebuild at about t = 660 s (about 11 minutes; on a failed refresh up to the 15 minute TTL on top). The same window applies to a doctor who just became bookable: absent from the name index (headline still matches) with no `meta.degraded`. For AV-R29: the key lives at most 15 minutes, but the names inside can be up to 300 s older than the build.
  - Rule: CLAUDE.md -> Documentation structure ("the contract is the source of truth"; contract first, then spec/ADR).
  - Decision: owner decision. Either (a) reword to "up to about 10 minutes (the Identity cache of 5 minutes plus the rebuild period)" and describe the new-doctor lag in contract, spec and ADR 0025, or (b) bypass `identity:user:*` in the builder (more Identity load: reuse is already close to zero, so the call count would not change much).
  - Fix: (a) is a wording change in three documents, contract first.
  - Test gap: none (documentation).

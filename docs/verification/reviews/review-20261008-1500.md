## High
- [x] RESOLVED — approve/reject now refuse with 409 Conflict + Retry-After 5 while the locked profile's identity_sync_status is pending, so an unapplied resubmit/reopen job is never superseded into a refused transition; contract `ApplicationDecisionConflict`, spec §6/§16; unit + integration tests (resubmit with Identity down -> approve/reject 409 -> worker syncs -> approve 200, Identity active) (src/app/verification/service/verification.service.ts decide, tests/integration/verification.test.ts decisionWaitsForPendingSync) (finding: Superseding an unapplied resubmit/reopen job makes a later approval send `rejected → active`, which Identity r)
  - Scenario: Doctor is `rejected` and Identity is `rejected` (synced). The doctor resubmits (or an admin reopens) while Identity is down, so job J1 (target `pending`) stays pending and the response is 202. An admin approves. `decide` calls `supersedePendingSyncJob` and inserts J2 (target `active`). Identity never saw J1, so it is still `rejected`, and `rejected → active` is outside the provider's allowed transitions (`pending→active|rejected`, `rejected→pending`; the contract's own 409 example is "from rejected to active"). J2 gets `409 InvalidStatusTransition`, so job and profile become `failed` and on-call is paged. The profile is `approved` with `identity_sync_status='failed'`, so the doctor is never bookable. Nothing in the module can repair it, because approved is not reviewable.
  - Rule: CLAUDE.md → Cross-service integration, Case 1 (steps 4-6); spec D3 and §6 (supersede), V6/V13.
  - Fix: Do not drop an unapplied intermediate step. Either (a) make the superseding job carry the full path (send `pending` first when the superseded job was an unapplied `pending` and the account is still `rejected`), or (b) refuse the decision with `409 Conflict` or `ApplicationNotReviewable` until `identity_sync_status` is `synced`. Add a test for the chosen behavior.
  - Test gap: No test for resubmit with Identity down followed by approval. The existing "resubmission while Identity is down" and "supersedes open job" tests stop before the second decision.

## Medium
- [x] RESOLVED — ObjectHead now carries the S3 ETag; promote(from, to, { etag, contentType }) sends CopySourceIfMatch and the type the service detected; the second read/sniff is gone (src/lib/storage/s3.adapter.ts:104, src/lib/storage/types.ts, src/app/verification/service/verification.service.ts complete); S3 unit tests, MinIO replace-after-HEAD test, fake-storage replaceAfterNextHead, service and route tests (finding: Stored bytes are verified, but the promoted object is not bound to the verified one (TOCTOU on the quarantine )
  - Scenario: The presigned POST stays valid for 300 s and the intent for 900 s. A doctor uploads a valid PDF, calls `complete`, and `headObject` plus `readHead` pass. Before `promote` runs its own `readHead` and `CopyObject`, the doctor re-POSTs different content to the same `quarantine/<uuid>` key with the still-valid policy. The copy takes the new object unconditionally (no `CopySourceIfMatch`/ETag, no `IfUnmodifiedSince`). `size_bytes` and `file_type` in the row come from the first check, and `ContentType` comes from `promote`'s second sniff. The second read only narrows the window, and the leading 16 bytes are the only thing ever checked. Unverified content can end up as the "verified" document, and size and type can disagree with the row.
  - Rule: CLAUDE.md → Security rules (row only after `complete` verifies the stored object itself); spec §6 step 6-8.
  - Fix: Return the ETag from `headObject`, pass it as `CopySourceIfMatch` in `promote`, and use the detected type from the service (drop the second sniff and read). Alternatively refuse `complete` until the POST policy has expired. Either way, add the `size_bytes`/type check to the copy result.
  - Test gap: No adapter or service test that overwrites the quarantine object between `headObject` and `promote`.

- [x] RESOLVED — idempotency removed from createIntent and both download-url routes; contract drops the header and 422 there and says so; route test proves no idem:* key in Redis and one audit row per issued URL (src/app/verification/routes.ts:24-30, contracts/openapi.yaml, tests/integration/verification.test.ts idempotencyNeverStoresSignedUrls) (finding: Optional idempotency on the URL-issuing routes stores presigned URLs and POST policies in Redis for 24 h and r)
  - Scenario: `POST .../download-url` with an `Idempotency-Key` stores the response body, including the signed GET URL, under `idem:*` for 24 h. A replay (same key and principal) returns the same URL with no new `verification.document_url_issued` row. The URL is already expired after 60 s, so the client gets a dead link, and the 24 h Redis copy is a credential store the design never intended. Replaying within 60 s hands out a URL with no audit row, which breaks "one audit row per issued URL". The same applies to the `createIntent` response (`url` and `fields`, which include the policy and signature).
  - Rule: CLAUDE.md → Security rules (download URLs issued on demand, audited, 60 s); Privacy and logging (audit before returning); spec §6 Download URL ("each issued URL has one audit row").
  - Fix: Do not mount `idempotency` on `download-url` and `createIntent`. Adjust the spec and contract (optional header and 422 on those operations) in the same change. Repeated calls already produce a fresh URL and audit row.
  - Test gap: No test that a replayed download-url call writes a second audit row or never serves a stored URL.

- [x] RESOLVED — listQueue runs two phases: (submitted_at, id) > (?, ?) as an index condition, then the NULL tail by id. EXPLAIN on real Postgres, 60k rows mid-queue: old Filter, 41,759 rows removed, 1,015 buffers, 7.6 ms; new Index Cond, 45 buffers, 0.14 ms. Route test pages timestamped rows then the NULL tail (src/app/verification/repository/verification.repo.ts listQueue) (finding: Keyset predicate cannot use the queue index)
  - Scenario: The index is `(verification_status, submitted_at, id)`, but the page predicate is `(COALESCE(submitted_at,'infinity'), id) > (?, ?)`. Postgres cannot use that as an index condition, so it scans and filters every earlier row of the status. Page N of `status=approved`, which grows without bound, reads N×limit rows.
  - Rule: CLAUDE.md → Performance rules 2 (index matches query shape); Database rules (composite = equality then range/sort).
  - Fix: For non-null cursors use `(submitted_at, id) > (?, ?)` (nulls sort last, so add `OR submitted_at IS NULL`). Handle the null-sentinel branch separately, then `EXPLAIN` the deep-page query.
  - Test gap: `EXPLAIN` or plan assertion for page 2 of the queue (spec §10 asks for it).

- [x] RESOLVED — dropped the no-op claim transaction (claimDuePendingJobs -> listDuePendingJobs) and the worker path re-checks next_attempt_at inside the per-doctor lock, so a second worker honours the first one's backoff; unit test plus two-worker route test asserting a single Identity PATCH (src/app/verification/service/verification.service.ts attemptSync, repository listDuePendingJobs) (finding: The worker's `SKIP LOCKED` claim does not claim anything, and a second worker retries immediately)
  - Scenario: `claimDuePendingJobs` runs `FOR UPDATE SKIP LOCKED` in a transaction that commits as it returns, so the rows are unlocked before they are processed. With two workers both receive the same ids. `processDueSyncJob` then re-checks status but not `next_attempt_at`. After worker A records a transient failure with a future `next_attempt_at`, worker B calls Identity again straight away, which defeats the backoff and doubles outbound traffic during an outage. The per-doctor advisory lock prevents concurrent calls, not repeated ones.
  - Rule: Spec §7 (due jobs, backoff, two workers allowed); CLAUDE.md → Case 3/1 retry policy (backoff).
  - Fix: Re-check `next_attempt_at <= now()` inside the locked section of `attemptSync` for the worker path, or drop the pointless claim transaction.
  - Test gap: Two-worker test where a transient failure reschedules, asserting a single Identity call.
